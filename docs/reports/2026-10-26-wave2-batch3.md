**CI now fails if a test would not run:**
- **Every test project runs in a job.** A test project in `Insys.slnx` outside `tests/Insys.*Tests`, which no job runs, fails CI.
- **Every compiled integration class runs.** Each shard lists the classes in the built assembly (`-list classes`). The check fails unless each is in a shard or is the sweeps class. ### 2. Timestamps stay UTC; the permission check
- **No timestamp became a date.** Every one of the 22 changes replaced a date with a date: `IClock.UtcToday` became `IBusinessDate.Today` or `TenantBusinessDates.TodayFor`, and `DateOnly.FromDateTime(instant.UtcDateTime)` became `IBusinessDate.DateOf(instant)`. Every `IClock.UtcNow` passed beside them is unchanged.
- **The payment timeout:**
  - The job still selects payments sent before `clock.UtcNow - UnknownAfter`, a UTC instant.
  - `PaymentOutcomeUnknown` carries the UTC instant.
  - `MarkUnknown`'s date argument feeds only the shared outcome step, which uses a date for a confirmed payment's value date. A timeout records no date.
  - The batch report's table said otherwise. It is corrected above, and so is `contract-changes.md`.
- **The permission check is cached at two levels:**
  - A resolved principal is cached for 30 seconds per tenant and subject.
  - On a cache miss, each `TodayFor` call is an in-memory lookup of the tenant's time zone (`TenantTimeZones`, a singleton). The time zone is read from the database at most once a minute per tenant per process.
- **Two gaps found and fixed:**
  - **One date per principal.** The resolver computed the business date up to five times while building one principal, so a principal resolved across midnight could mix two dates. It now reads the date once and passes it through.
  - **Cached permissions ended up to 30 seconds after midnight.** A principal cached at 23:59:50 kept a role ending that day for up to 30 seconds past the tenant's midnight. Each cache entry now also ends at the start of the tenant's next business date (`TenantBusinessDates.StartOf`). The cache checks that end against `IClock`, so it holds under a test clock too.
  - **Test:** `APrincipalCachedBeforeTheTenantsMidnight_LosesARoleEndingThatDay_AtMidnight_BR040`. At 21:59:50 UTC the role's screen returns 200; 20 seconds later it returns 403. Without the fix the test fails, with 200 instead of 403.

### 3. The end-to-end tests between 22:00 and 24:00 UTC
**Cause: an inconsistent test clock, not the application.**
- The end-to-end hosts ran with `BusinessDate:TestDate`, which fixed every tenant's "today" to the UTC date the run started.
- Instants still came from the real clock, and `IBusinessDate.DateOf` converts them to the tenant's zone.
- Between 22:00 and 24:00 UTC, Johannesburg is already on the next date, so "today" and the dates of instants disagreed by a day. Each failure is that disagreement:
  - **General F101:** the claim notice says "REGISTERED (27 October)", the registration instant's local date, where the test expected the 26th.
  - **General F103, and Enterprise quote to cash:** written premium was projected to the local date of the event, so the test's "today" (the UTC date) showed none.
  - **Enterprise closed period:** GWP was dated by the event's local date, so the report for the UTC "today" read 0.

**Fix: a fixed clock inside the window.**
- The end-to-end hosts now run on `WindowClock` (`Insys.Testing`). It starts at 22:30 UTC on the latest day that time has passed and advances in real time. Timers and the outbox are unaffected.
- The hosts take no test date. They convert instants as production does, and the tests expect the tenant's date (`WindowClock.Today`, the UTC date plus one in Johannesburg).
- Every run, at any hour, therefore exercises the window. The suite takes about 5 minutes locally and about 8 on CI, against 90 minutes before midnight UTC.
- The GAP-044 boundary test keeps its own fixed instant (23:30 UTC on the same day).

**Results:**
- **This branch:** all 31 end-to-end tests pass on the window clock. The run started at 06:14 UTC, so the hosts read 22:30 UTC.
- **`main` (`ea84183`) with only these test changes:** 30 of 31 pass.
  - The four tests that used to fail now pass. Their cause was the test clock alone.
  - `DeathClaim_…_LIF008` fails with 422 instead of 201. On `main`, `LifeClaim.NotifyClaim` refuses an event dated today in Johannesburg as "in the future", because it compares against the UTC date. BR-040 fixed this.
  - So CI now proves the business date fix on every run, whatever the hour. Before this change, that defect could only show between 22:00 and 24:00 UTC.
