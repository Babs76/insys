# BR-121 / GAP-125: a filed appointment letter isn't the endorsement's document

**The defect:** filing a letter raises `DocumentGenerated`, and General's handler attached any such document as the endorsement's own. That moved the version, so a submit with the filing's version was refused, and the real document could no longer attach.

**The fix:** General attaches a document only if it came from a template and its category is one the endorsement type produces. A filed document has no template.

**A second cause, found by the test:** the filing's response reported the version from before the save, so its ETag was one behind and a submit with it was refused anyway. This handler now returns the version after the save.

**The sweep of `DocumentGenerated` handlers:**
- **Health's remittance handler** had the same loose match; it now requires a template.
- **General's `PolicyEffects`** records every document on a policy as an effect. That is its purpose and it writes no version on the policy, so it stays.

**Tests:** an end-to-end test files the letter, drains the events, finds the version unchanged, submits with the filing's ETag, and finds the real document attached and the letter only in `appointmentLetterId`.

**No data repair:** nothing is in production, and the front end hasn't seen a record with this. Any test tenant's bad rows would be `document_id = appointment_letter_id`.

## Decisions for Ade
**Other changes have the same stale response.** A command that returns its view built from the aggregate before the save returns the old `rowVersion` and ETag; 43 places already add one by hand, and many don't (for example `DecideClinicalReferral`). A client using the response's version instead of a fresh GET gets 412. *Recommendation: fix it once in the unit of work, setting the returned view's version after the save, on its own branch with a test on a sample of each kind; about 2 days. Until then the front end should read after a change, as it mostly does.*
