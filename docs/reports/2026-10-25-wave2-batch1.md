## Approval endings fixed (D-1 to D-5, signed off)
**The rule:** every way an approval can end (approved, rejected, expired, withdrawn) leaves its record in a defined state, never waiting forever. Built across Workflow and twelve modules (two agents in separate worktrees, merged here), with V0056.
- **D-1:** a payout batch whose approval does not end in approval ends `Rejected`; its unsent payments leave the batch and the next batch takes them (never in two live batches, never paid twice).
- **D-2:** a provider payment run ends `Rejected` and its claims are released for a new run. The table test found that a database trigger (`health.keep_payment_run`, V0020) refused to clear a claim's run and rolled the ending back; V0056 lets a claim leave a run that has not been approved, and only to no run.
- **D-3:** a new bank account waits while the previous one stays active; approval supersedes the previous, any other ending rejects the new one. V0056 replaces the one-current-account constraint with one active and one waiting per party and currency.
- **D-4:** expiry and withdrawal reach the owning module as an ending (`workflow.ApprovalRejected` gains `ending`); the requester can withdraw their own request (`POST /workflow/approvals/{id}/withdraw`); the requester gets a follow-up task on expiry or a module's withdrawal; expiry is per approval type (`workflow.cfg_approval_expiry`, 14 days by default). The table test found static data changes ignored endings with no checker; fixed.
- **D-5:** an ending a module cannot apply parks with `APPROVAL_ENDING_NOT_APPLIED` (ADR-022: shown, escalated, retried). A redelivered ending already applied succeeds without change. A module refusing an *approval* still behaves as before (outside D-5 as worded; see open points).
- **OQ-113:** every record an approval is about shows `latestRejection` (who, when, the reason, and how it ended).
- **OQ-112:** authority limits carry a currency (V0056). Proposed: retire `payment.cfg_payment_release_limits` (open).
- **The table-driven test** (`ApprovalEndingsTests`): 18 approval types × approved, rejected, expired, withdrawn = 72 rows, each in its own tenant, driven through the real Workflow endpoints and expiry job, checking the record's state against the guide's table, `latestRejection`, the follow-up task, nothing parked, and for D-1 and D-2 that payments and claims are released. **72 passed.**
- **Guide §1** is rewritten to the fixed behaviour; `contract-changes.md` lists the changes.
