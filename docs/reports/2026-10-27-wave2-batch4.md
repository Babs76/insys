## A create's ETag is the version it saves (defect found in the full run)

The full run on the batch failed a record-hold release with 412. The create's response, made before the save, carried `rowVersion` 0 and ETag `"0"`, but the save writes version 1, so a change quoting that ETag was refused. GL exports had the same defect from before batch 4: a batch could not be acknowledged with its create's ETag. **A new aggregate now starts at version 1** (`AggregateRoot.RowVersion`), so every create's view and ETag carry the version saved. The other failures from that run were the older tests meeting the new If-Match rule. ## BR-087: static data paging lost the row on a page boundary (defect, first in the batch)

### What was wrong
`StaticDataService.ListInForce` asked the database for the codes after the cursor (`string.Compare(code, after) > 0`) and ordered them (`ORDER BY code`), both under the database's collation, en_US, which ignores underscores at the first level. It then re-sorted the page ordinally (`Overlay`, `StringComparer.Ordinal`) and gave the last code as the next cursor. The two orders disagree wherever an underscore meets a letter: en_US gives `PGA, PG_A, PGB, PG_B`, ordinal gives `PGA, PGB, PG_A, PG_B`. A code that the database put before the cursor but the ordinal sort put after it was never returned. In the function catalogue (687 rows, 200 a page) that was `SD_BENEFIT_MANAGEMENT_MAINTAIN`, as the front end found.

### What changed
- `StaticDataService.ListInForce` compares and orders the code with `EF.Functions.Collate(code, "C")`: bytewise, which is the ordinal order for the ASCII codes static data uses. The cursor, the database's order and the overlay's sort now agree, whatever the database's default collation.
- `ProductList.List` (`GET /api/v1/product-factory/products`), the only other list paged by a text key, does the same. It had no in-memory re-sort, so it did not lose rows, but its order depended on the server's collation.
- `ComplianceStores.ReturnStatuses` (the returns summary's period range, not a paged list) compares period codes bytewise too, so every text comparison in a query follows one rule.

### The sweep: every cursor-paged list
| Lists | Cursor | Finding |
|---|---|---|
| Every static data table's list (270 tables, the generic `MapStaticEntity`) | text: the code | **Lost rows (BR-087).** Fixed. |
| Product list (`ProductFactoryListProducts`) | text: the product code | Consistent (compared and ordered in SQL alike), but in the server's collation. Fixed to bytewise. |
| Payments, Identity (users, grants, reviews), Party (search, search log), General (quotes, policies, claims, portal lists, aggregation alerts), Tenancy, Integration (dead letters, parked deliveries, webhook deliveries), Health (9 lists), Life (5 lists), Distribution (2), Reinsurance, Static Data governance (change requests, import batches), Audit (2), Workflow (cases, portal cases, approvals, processes), Finance GL exports, Documents record holds, Billing portal, Communications (2) | UUID (UUIDv7) | Not affected: each compares and orders the `uuid` column in SQL, and none re-sorts in memory. `uuid` ordering has no collation. |

### Tests
- `StaticDataPagingTests` (integration):
  - `PagingAStaticDataList_ReturnsEveryCodeExactlyOnce_WhenCodesStraddleAPageBoundary_BR087`, at page sizes 1, 2, 3 and 5: tenant and global codes (one overlaid) chosen so en_US and bytewise orders disagree. Every code comes back once, in bytewise order. It first checks that the test database's collation ignores underscores, so it cannot pass vacuously.
  - `PagingTheFunctionCatalogue_At200APage_ReturnsEveryFunctionExactlyOnce_BR087`: pages the whole catalogue at 200 and compares it with the in-force codes read straight from `iam.ref_function_catalogue` (including `SD_BENEFIT_MANAGEMENT_MAINTAIN`).
  - With the fix reverted, all five fail; with it, all five pass.
- `TextCursorCollationTests` (architecture): a text comparison in a query's `Where` must name its collation, so a new text-keyed list cannot reintroduce the defect.

## Static data required fields: catalogue, validation and contract agree (BR-084, BR-085)

### What was wrong
The front end's live runs found fields the API requires but treats as optional:
- a Health plan option's `productCode` (BR-084);
- a case type's `processCode` and `appealRoute` (BR-085).

Ade asked for one sweep over every static data table instead of fixing these one by one. The sweep compared, for each of the 270 tables:
- the catalogue's `mandatory` flag;
- the generated input's validation;
- the rules modules write themselves;
- the OpenAPI input schema.

It found four kinds of disagreement:

1. **The contract declared no required field at all.** No static data input schema had a `required` list, so every field looked optional to a client. This is why BR-085 was raised: the catalogue already marked `processCode` and `appealRoute` mandatory, and the API already required them.
2. **The catalogue marked a field optional that a module's own rule always requires.** The fields:
   - `health.cfg_plans_and_options.product_code`, required at submit by `PlanProductsGuard` (BR-084);
   - `channel.cfg_channel_transaction_permissions.function_code`, required by `ChannelRowValidator`;
   - `iam.cfg_segregation_of_duties_conflict_rules.function_a` and `function_b`, required by `DutyConflictRuleValidator`.

   The last three were missing from the catalogue altogether.
3. **The catalogue marked mandatory four fields that ADR-026 retired, which must be empty:**
   - `channel-transaction-permissions.transaction_type`;
   - `roles-and-permission-sets.permissions`;
   - `segregation-of-duties-conflict-rules.permission_a`;
   - `segregation-of-duties-conflict-rules.permission_b`.
4. **35 columns added by migrations after the original specification were not in the catalogue** (the list below). For the seven that are NOT NULL, the API already required the field but the catalogue did not list it.

No column the database requires was marked optional in the catalogue, and no field the generated validation requires was missing from the catalogue, apart from those 35.

### What changed
- **The catalogue's mandatory flag is now the single source.**
  - The generator (`tools/Insys.StaticData.Generator`) requires a field when its column is NOT NULL or the catalogue marks it mandatory.
  - It stops with a list of every disagreement when:
    - a catalogue field has no column;
    - a column has no catalogue field;
    - a NOT NULL column is marked optional.
  - It puts `[RequiredField]` on each required input property, and the OpenAPI documents list those properties, with `code` and `changeReason`, as `required`.
- **Four checks moved into the generated validation:** `productCode`, `functionCode`, `functionA` and `functionB`. They are now refused when a draft is saved or an import line is read, with "`<field>` is required.".
  - The modules' own null checks for `functionCode`, `functionA` and `functionB` were removed as duplicates.
  - The Health plan guard keeps its submit check, for drafts saved before this change.
- **The OpenAPI documents** (`openapi-static-data.json`, `openapi-platform-operator.json`) were regenerated. Every static data input, and the lines of its import, now has a `required` list.
- **The test that fails the build:** `tests/Insys.ArchitectureTests/StaticDataRequiredFieldTests.cs`, two theories over every static data table:
  - `TheFieldsTheApiRequires_AreTheCataloguesMandatoryFields_BR084_BR085`:

Product definitions are excluded: the ProductVersion aggregate writes them through its own operations, so there is no static data input.

## BR-073: a reason or code that is too long is a 422 field error (defect)

## Concurrency: BR-031, BR-057, BR-064, BR-071
**The approach: one generic mechanism, not a handler change for each of 88 operations.**
- **`.TakesIfMatch()` on an endpoint:** requires If-Match (428 without it, 412 when it cannot be read), and puts the expected version on the request.
- **The unit of work** (`TransactionalCommandHandler`) compares the expected version with the version of the aggregate the command changed, as it was loaded: the modified aggregate, or else the only one it loaded. A command changes one aggregate (the project's rule). When they differ, it answers 412 and writes nothing. A stale version is answered before any refusal by the domain, as HTTP evaluates preconditions first. The update still checks `row_version`, so a change committed in between is a conflict too.
- **`.ETagsFromRowVersion()` on each module's staff route group:** every read, and every change that returns the record, sets the ETag from the record's `rowVersion`.
- **`rowVersion`** was added to the two views that lacked it: the claim payment instruction and the General proposal.

**Scope:**
- **If-Match:** 88 operations across General, the claims framework, Billing, Distribution, Life and Health. Every write in those modules that had neither header.
- **Idempotency-Key:** 8 creates (the claims framework's seven and `DistributionPrepareStatement`).
- **Neither:** `HealthCheckEligibility`, which changes nothing.

**Tests:**
- `ConcurrencyContractTests` (architecture, on the committed contract):
  - every write in the six modules takes If-Match or an Idempotency-Key;
  - every record an If-Match change is on has a read that returns its `rowVersion`.
- `ConcurrencySweepTests` (integration, every endpoint): each If-Match change refuses a request without it with 428, for a caller who holds its permission.
- `GeneralProcessTests` (end to end): two people on one claim; a change with the version read before the other's change is 412.

**Test clients:** the flow tests written before this sent changes without If-Match. Their client (`TestPreconditionsHandler`, test library only) resends a change answered 428 once, with the ETag of the record's own read, and a create answered `IDEMPOTENCY_KEY_REQUIRED` with a new key. So each flow test also proves that every record it changes gives an ETag. The sweeps send requests raw.

## BR-016: a static data import approved as one change
**Built as signed off, with the three conditions:**
- **Every static data table gains `import_batch_id`** (V0067, one loop over the tables `sdm.guard_static_version` guards). An import's drafts carry their batch. A line is submitted only with its import (409 alone).
- **Submitting an import** checks every line as a draft alone is checked (period, retroactivity, the module's own guards). All the lines then go to pending approval under one change request (action `IMPORT`, `sdm.change_request.import_batch_id` and `import_hash`), and Workflow is asked for one approval of the table's tier. Tier 2 with maker-checker off, and Tier 3, are approved on submission, as a single draft would be.
- **The checker sees every line:** `GET …/imports/{batchId}`, in code order.
- **Approved or rejected as a whole:** the approval approves every line in one transaction. A rejection, expiry or withdrawal returns every line to draft, and the corrected import is submitted again as a new change.
- **Bound to the hash of the complete import:** the SHA-256 over every line's full record, without the fields the approval itself changes. If a line changed after submission, the approval is not applied and parks (`APPROVAL_NOT_APPLIED`), and no line is approved.
- **Activated together:** `POST …/imports/{batchId}/activate`.

**Differs from proposal §2:** `sdm.import_batch` keeps its statuses. The import's state is its change request's status, and each line's.

**Limit:** a table's guards across codes (overlapping bands, say) check a line against the codes already in force or on their way, not against the other lines of its import.

**Tests:** `StaticDataImportApprovalTests` (4):
- a 100-line import approved with one decision, seen line by line, and activated together;
- a rejected import, corrected and approved as a new change;
- a line changed after submission: not applied, parked, and no line approved;
- Tier 2 with maker-checker off, approved on submission.
