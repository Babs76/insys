# BR-061 (group A, hotfix to `main`): a new environment is no longer deadlocked

**Branch:** `br-061`, from `main` at `ea84183`. It merges to `main` on its own once CI is green, before the rest of Wave 2 batch 3 (Ade, 27 October 2026).

## The defect
The front end's first live run against `ea84183` found it:
- `wave2-2` made `TERMINATE_TENANT` privileged.
- The bootstrap's `PLATFORM_ADMIN` role takes every function under `tenant.update`, so it became privileged too.
- A fresh environment has one operator. Assigning `PLATFORM_ADMIN` to a second operator needs a second person's approval, and there was no second person.

**Two more gaps made it worse:**
- `PLATFORM_ADMIN` held no Workflow approval permissions, so even two bootstrapped operators could not have decided anything.
- The operator tenant had no approval authority rows (WFL-004), so a `PRIVILEGED_ROLE` approval had no one entitled to give it.

## The fix (Ade's decision)
- **Two administrators from deployment configuration.** The bootstrap creates two platform administrators, two distinct named people: `--admin1-subject`, `--admin1-username`, `--admin1-name` and the `--admin2-` equivalents, or `INSYS_BOOTSTRAP_ADMIN1_…` and `INSYS_BOOTSTRAP_ADMIN2_…`. This is the platform's equivalent of BR-013's two first administrators. There is no approval bypass beyond the bootstrap's own two assignments, and no single-operator mode.
- **Refused at start-up:** one administrator, an incomplete one, or the same subject or username twice. The message names the settings, and nothing is created. The old `--admin-subject` is refused with the same message.
- **`PLATFORM_ADMIN` also holds `approval.read` and `approval.approve`,** so it has the Workflow approvals inbox.
- **The role gets approval authority for `PRIVILEGED_ROLE` and `TENANT_ADMINISTRATOR`** in the operator tenant.
- **The bootstrap can run again:**
  - Run twice, it changes nothing.
  - On an environment bootstrapped with one administrator before this fix, it adds the second, which is the way out for a deadlocked environment.
  - It refuses a configured person who would be a third. More administrators are added through the API, with approval.
- **The local Keycloak realm** gains `insys-admin-2` (`sub` `0199f000-0000-7000-8000-0000000000a2`).
- **Documents:** `docs/runbooks/deployment.md` and the README's configuration table are updated.

## Tests (`PlatformBootstrapTests`)
- **From a database with no tenant:**
  - the real bootstrap with two administrators;
  - both sign in (`/identity/me`, 200);
  - one assigns `PLATFORM_ADMIN` to a third operator, the assignment that deadlocked;
  - it waits for approval, the requester cannot approve it (`MAKER_CHECKER_SAME_PERSON`), and the other administrator approves it, so it becomes `ACTIVE`.
- **Refused at start-up with a clear message, with nothing created:** a single configured operator, the same person twice (with the username differing only in case), or an incomplete administrator.
- **Run again:** nothing changes, and a third configured administrator is refused.

## Other functions `wave2-2` made privileged: no other hard deadlock
| Function | Who holds it | Deadlock? |
|---|---|---|
| `TERMINATE_TENANT` | `PLATFORM_ADMIN` (operator tenant) | **Yes. Fixed here.** |
| `CASE_RECORD_REDRESS`, `CASE_REOPEN`, `CASE_PLACE_LEGAL_HOLD`, `CASE_RELEASE_LEGAL_HOLD`, `CASE_DECIDE_APPEAL` | Roles in a business tenant (complaints) | **Not a hard deadlock, but only an awkward way through until BR-013 is merged.** |

**Why the case functions should not be a hard deadlock on `main`:** a role holding any of them is privileged, so assigning it needs a second person in the tenant with `PRIVILEGED_ROLE` authority. On `main` a new tenant has one first administrator and no authority rows. **Reading the code** (this path is not tested), that administrator can still get there:
1. Create a second user with a non-privileged role (static data and approvals, which needs no approval).
2. Propose the authority rows, which that user approves.
3. Assign the privileged role, which that user approves.

**BR-013, on `wave2-3`, gives the proper path:** two first administrators, and `TENANT_ADMIN` authority put in force with them.

`STATIC_DATA_CHANGE_TIER2_MAKER_CHECKER` was privileged before `wave2-2`, and the same applies to it.
