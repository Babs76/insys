1 · Scope and provenance

A domain model built on the SRS boundaries

The SRS fixes the main boundaries: separate Life, General and Health domains that own their policies, claims and rules, with shared services where their meaning genuinely matches (§1.1, §8.1, §21.3). This document turns those boundaries into a working domain model.

2 · Design rules

Rules every context follows

Aggregates

  • One command changes one aggregate in one transaction.
  • Invariants hold inside an aggregate at all times. Rules that span aggregates are made eventually consistent through events.
  • Aggregates refer to each other by ID only, never by object reference across boundaries.
  • Aggregates are kept small. Heavily contended data, such as health benefit usage, gets its own aggregate.
  • Every aggregate belongs to exactly one tenant and one context.

Commands and events

  • Commands are imperative (IssuePolicy) and may be rejected. Events are past tense (PolicyIssued) and are facts.
  • Commands that move money or create records carry an idempotency key (INT-003, PAY-001).
  • Events are published from an outbox in the same transaction (§23.2), carry tenant, version, correlation and causation IDs, and minimise sensitive data (INT-007).
  • Consumers tolerate duplicate and out-of-order delivery (INT-005).
  • Transactions record the configuration versions they used (PRD-008).

Customer–Supplier

The upstream team plans around the downstream team's needs. Used where domains feed Billing, Reinsurance and Commission.

Open Host Service and Published Language

An upstream context offers a stable, versioned API or event schema for many consumers. Used for Party, Rating, Rules, Claims Framework and Product versions.

Anti-corruption layer and Conformist

Integration translates external partner models so they never leak into domains. Finance translates business events into postings through posting rules, rather than adopting each domain's model.

7 · Cross-context processes

Processes that span contexts

Each process is choreographed through events, with Workflow orchestrating human steps. Compensations show what happens when a step fails. Commands are decisions within one aggregate, events are facts, and policies are the reactions of other contexts.
