1 · Scope and decisions

What this specification covers

This document specifies the database artifacts behind each module: the tables that hold aggregates, shared entities, logs, work items, integration records and projections. Static data tables are specified separately and only referenced here.

In scope

  • Domain aggregates from SRS §21.2
  • Shared entities from SRS §21.1
  • Append-only logs: audit, financial, decisions
  • Workflow, exception and queue tables
  • Outbox, inbox and idempotency tables
  • Read projections for analytics

Covered elsewhere

  • The 253 static data entities: one table each, defined field by field in the Static Data Specification
  • Document content, held in object storage (only metadata is here)
  • Metrics, logs and traces, held in the observability stack
  • Secrets, held in the secrets manager

Database decision

PostgreSQL is the platform database, decided on 21 October 2026. This settles the database part of the §30 technology stack question. Types, row-level security, partitioning and DDL in this document are written for PostgreSQL. Version and hosting choices are still open (section 11). Record the decision as an ADR; the SRS register has no dedicated one, so ADR-012 is proposed.

Provenance. The SRS defines aggregates and ownership rules but no tables, columns or keys. Every table, column, index and DBA-prefixed requirement here is a proposal for review. The generated DDL has been run against PostgreSQL 16 and its isolation behaviour tested (section 9). Tables for which §21.2 defines no aggregate (for example Life maturity, Group Life, General underwriting referrals and reinsurance) are marked as proposed in their notes. Sample values are illustrative, and party names and identifiers are fictitious.
2 · Schemas and ownership §21.3 · §4.3

One schema per module, written only by its owner

Each module owns one schema. Only that module's service role may write to it. Other modules read through APIs or events, never by querying another module's tables. This applies the SRS data ownership rules: domains own their data, no domain writes into another's database, and cross-domain interaction uses APIs or events (§21.3).

SchemaOwning moduleLayerTables

Profile A · Shared

All tenants share one database cluster. Every row carries tenant_id and row-level security filters each query. This is the default.

Profile B · Dedicated database

The same schemas are deployed in a database for one tenant. tenant_id and row-level security stay in place as defence in depth, so the code path does not change.

Profile C · Dedicated environment

A separate cluster in a separate environment, with the same schemas. Backup, restore and region are set per tenant.

Naming conventions

  • Schemas and tables in lower snake_case, singular nouns: life.policy, not Life.Policies
  • Foreign keys named after the target: policy_id, billing_account_id
  • Cross-module references end in _ref or _id and carry no foreign key
  • Business numbers end in _number or _code and are unique per tenant
  • Static data tables use ref_, cfg_ or mst_ prefixes
  • Index names: ix_<table>_<columns>; unique: uq_; check: ck_

5 · Tenant isolation in the database §4.2 · TEN-002 · TEN-004

Row-level security as an independent control

The SRS states that application-level filtering alone is not enough (§4.2). Every tenant-scoped table therefore enables and forces row-level security. The application sets the tenant for each transaction from the authenticated context, and the database refuses rows from any other tenant even if a query forgets its filter.

-- Applied by migration to every tenant-scoped table
ALTER TABLE life.policy ENABLE ROW LEVEL SECURITY;
ALTER TABLE life.policy FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON life.policy
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- Set by the data-access layer at the start of every transaction,
-- from the authenticated principal, never from request input (TEN-002)
SET LOCAL app.tenant_id = '3f9c2a1e-…';

Fails closed

If app.tenant_id is not set, the policy expression raises an error and the query fails, rather than returning every tenant's rows. In a new connection the error is an unknown setting; on a pooled connection where the setting was used before, it is an invalid empty UUID. Both were confirmed in testing.

Database roles

  • Migration role owns each schema and runs DDL only
  • One service role per module, with DML on its own schema
  • Application roles never own tables and never have BYPASSRLS
  • Reporting role reads replicas only

Beyond tables

Caches key on tenant_id, search indexes filter by it, events carry it, and object storage paths start with it (TEN-004). Isolation tests in §27.4 run against the database directly as well as through the APIs.

6 · Common patterns

Patterns applied across modules

Transactional outbox §23.2

Each module writes its domain events to its own outbox_event table in the same transaction as the business change. A relay publishes them and sets published_at. A committed change can therefore never lose its event.

Inbox and idempotency INT-003 · INT-005

Consumers record each processed event ID in an inbox table under a unique key, so duplicates are skipped. Non-repeatable API calls store an idempotency key with a request hash and the original response.

Append-only financial records FIN-002 · FIN-003

Journals, subledger entries, allocations, claim financial movements and commission clawbacks are never updated or deleted. The service role has INSERT and SELECT only. Corrections are new rows that reference what they reverse.

Version references PRD-008

Transactions store the version of every configuration they used: product, rating, rule set, posting rule, template, commission plan and cession rule. Any result can be recalculated as it was.

History without soft delete

Transactional records are not deleted or flagged as deleted. They move through status transitions, with history kept in event or log tables. Personal data is anonymised in place when retention ends, keeping financial totals intact.

Sensitive columns §24.1 · HLT-008

Identity numbers and bank details are encrypted by the application, with a keyed hash for lookups. Medical columns sit behind column-level grants and purpose-specific views. Event payloads carry references, not sensitive values.
