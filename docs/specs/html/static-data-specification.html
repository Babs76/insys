Requirements for maintaining reference data, configuration and master data across every layer, module and sub-module of the platform. It covers what must be maintained, its data points, data types and sample values, who maintains it, under which controls, and in what order it is loaded for a new tenant.

1 · Scope and provenance

What this specification covers, and how much of it comes from the SRS

Static data is any data that governs or classifies transactions, changes far less often than the transactions it governs, and is maintained deliberately by authorised people rather than produced by business processing.

In scope

  • Code lists and classifications
  • Versioned configuration: product, rating, rules, workflow, templates, posting rules
  • Master registers: providers, intermediaries, reinsurers, partners, banks
  • Platform reference data: countries, currencies, languages, calendars

Out of scope

  • Transactional records: policies, claims, invoices, payments
  • Customer party records, which Party Management maintains through business processes
  • Secret values such as API keys and passwords, which are held as references only
  • Infrastructure configuration outside the application

Provenance in this document

SRS The SRS names this data item as configurable or maintained.

Derived Not named, but an SRS requirement or sub-module cannot work without it.

Proposed Good practice we recommend. It is not implied by the SRS.

Important. The SRS has no static or reference data management section, no module for it, and no requirement IDs. Sections 2 to 6 and 8 are a proposed extension. The SDM-prefixed requirements are proposed IDs, not SRS identifiers. Governance tiers, scopes and owners are our recommendations for review.
2 · Classification

Every item has a class, a scope and a governance tier

Class

REF Reference data. Code lists that classify or describe, such as occupation classes or claim status codes.

CFG Configuration. Parameters, tables, rules, definitions and templates that change system behaviour, such as rating tables or posting rules.

MST Master data. Registers of real organisations the platform deals with, such as providers, intermediaries and reinsurers. They change slowly and follow the same controls.

Scope

G Platform-global. Maintained by the Platform Administrator and read-only to tenants. Example: ISO 4217 currencies.

GT Global baseline, tenant extension. The platform publishes a baseline. A tenant may deactivate, relabel or add its own codes, but never change a global code.

T Tenant-owned. Entirely inside the tenant boundary and isolated under TEN-006.

Governance tier

Tier 1 Critical. Affects price, cover, money movement, accounting, security or tenant isolation. Requires maker-checker, versioning, effective dating, impact analysis and a test or simulation before activation.

Tier 2 Controlled. Affects processing behaviour or customer-facing output. Maker-checker is on by default but a tenant may switch it off. Versioned and effective-dated.

Tier 3 Descriptive. Labels and descriptive lists. Changed by one authorised maintainer, with an audit trail.

4 · Governance and lifecycle

How static data changes

Reference and master data lifecycle

Draft→Pending approval→Approved (scheduled)→Active→Deprecated→Retired

Deprecated: no new use, existing references remain valid. Retired: hidden from all selection, history kept.

Configuration lifecycle (§7.7)

Draft→Validated→Submitted→Approved→Published→Effective→Withdrawn / Retired

Published versions are immutable (PRD-002). A change always creates a new version (PRD-003).

Rules that apply to every tier

  • A code that any record references cannot be deleted. It can only be deprecated or retired, with a replacement mapping where needed.
  • Promotion from test to production happens through an approved, audited configuration package, never by re-keying (§26.2).
  • Every change is audited with actor, tenant, target, before and after values, time and outcome (IAM-006).
  • Tenant changes never alter a global baseline. They create a tenant-scoped overlay.

Sensitive static data

  • Bank account, provider payment and intermediary payment details are Confidential and masked by default. Each view is audited (PAY-004).
  • Integration credentials are never stored as static data. Records hold a reference to the secrets manager only (TEN-006, IAM-004).
  • Clinical code lists are Public, but any configuration linking them to a named member is not static data.
5 · Static Data Management module Proposed · Layer 03

One shared service to maintain and serve static data

We recommend a single shared module that provides the maintenance, approval and distribution machinery. Each owning module keeps its own business definitions and validations: the Product Factory still owns product versions, and the subledger still owns posting rules. This follows the SRS principle of sharing infrastructure where semantics align (§8.1).

Sub-modules

  • Static data catalogue and ownership register
  • Code list maintenance
  • Change requests and maker-checker
  • Versioning and effective dating
  • Impact analysis
  • Bulk import and export
  • External standard synchronisation
  • Data quality rules
  • Distribution API and change events
  • Tenant-aware caching
  • Environment promotion packages
  • Audit, history and as-at queries

Components

  • Reference data store, tenant-partitioned
  • Change request workflow, using shared Workflow (§19)
  • Validation engine with per-entity rules
  • Bulk loader with staging area
  • Read API with as-at date parameter
  • Change event publisher, using the transactional outbox (§23.2)
  • Tenant-aware cache with event-driven invalidation (TEN-004)
  • Package exporter and importer for environment promotion

Proposed events

Not in SRS §23.1. Each carries the §23.2 metadata: event ID, tenant ID, type and version, timestamp, correlation ID.

  • StaticDataChangeSubmitted
  • StaticDataChangeApproved
  • StaticDataVersionActivated
  • StaticDataCodeDeprecated
  • StaticDataImportCompleted
  • StaticDataImportRejected

8 · Tenant load sequence Proposed · from data dependencies

Order of loading static data for a new tenant

Each step depends on data from the steps before it. This sequence would sit inside the tenant onboarding workflow required by TEN-008.

Platform reference data

Countries, subdivisions, currencies, languages, time zones, holiday calendars and units. These are usually already present, so this step only checks coverage for the tenant's markets.

Tenant registration

Tenant record, isolation profile (A, B or C), feature entitlements, operational limits and locale defaults.

Organisation and access

Legal entities and branches, roles and permission sets, segregation-of-duties rules, identity provider federation, and security policies.

Financial foundations

Chart of accounts, transaction types, accounting calendar, tax codes, account mappings, posting rules and tenant bank accounts. Posting rules are simulated before activation.

Shared operational set-up

Party code lists, consent purposes, document categories and retention schedules, templates, business calendars, workflow definitions, queues and authority matrices.

Payments and distribution

Payment methods, provider and bank register, reconciliation rules, intermediary register, distribution hierarchy and commission plans.

Domain reference data

For each domain in scope: occupation and lifestyle codes; vehicle, property and marine directories; the provider register, tariffs and clinical coding; and panels of adjusters and repairers.

Product Factory

Coverages, benefits, limits, exclusions, rating factors and tables, rule sets, questionnaires, product versions and template assignments. Products are validated, simulated, approved and published.

Reinsurance

Reinsurer register, treaties, cession rules and bordereaux layouts. These need published products to allocate exposure against.

Integration and reporting

Partner registrations, credential references, webhooks, code mappings, regulatory return definitions and report access rules. End-to-end tests (§27.3) then run against the loaded set.
